- (decision) Process lifecycle: long-lived pty per open thread. Backend spawns a Claude Code CLI pty process the first time a DM/channel thread is opened and keeps it alive (idle) between turns rather than resuming per-turn via session id. Prevents: per-turn cold-start latency and cross-process 'is this persona working' tracking. Requires an idle-reap policy (thread inactive N minutes -> kill pty, next message respawns/resumes).
- (decision) Stack: Node.js/TypeScript backend (node-pty for real Claude Code CLI process wrapping, ws for the pty-output-to-browser stream) + React/Vite frontend. Reason: node-pty is the established way to wrap a TTY-attached CLI process (same approach VS Code's integrated terminal uses); one language end-to-end; matches the plain-HTML mockups already produced in the UX spine.
- (decision) Party-mode channels run as ONE pty invoking the existing bmad-party-mode skill in its default 'session' mode (one Claude Code process voicing every persona inline, turns marked '{icon} **{name}:**'). Backend parses those turn markers for per-persona attribution. Prevents: multiplying pty processes per channel and inventing bespoke backend orchestration that edges toward the rejected separate-agent-runtime non-goal.
- (decision) Pty output is turned into structured chat events via a headless terminal emulator (render raw pty bytes into a clean, de-flickered text buffer, e.g. @xterm/headless) followed by a line classifier over that rendered buffer that detects message/tool-call/subagent-card/turn boundaries. Prevents: regexing raw ANSI bytes directly, which breaks under redraws/spinners/cursor repositioning.
- (decision) Persistence: SQLite via better-sqlite3, single local .db file (projects, threads, messages, personas tables). Reason: transactional writes and queryable cross-thread listing for a hobby single-user app, still a single file to back up; preferred over flat per-thread JSON files which have no query layer.
- (constraint) [ADOPTED from SPEC.md] Project activation fix: on room open/creation, backend ensures the pty spawns with cwd = the real project checkout (never a symlink directory), and overlays BMad's canonical skills/_bmad into that checkout via symlinks whose paths are excluded through that repo's .git/info/exclude (never a committed .gitignore). This is the root fix for the historical @-mention/misrouted-artifact bug and is fixed in direction, not open for reconsideration.
- (constraint) [ADOPTED from EXPERIENCE.md] Local web app: browser UI (React) talks to a local backend daemon over the same machine; no auth surface (single user, single machine, hobby project). Theme follows OS prefers-color-scheme on first load, then a remembered manual toggle. Desktop-width only for v1, no mobile/responsive requirement.
- (decision) Design paradigm: Actor model. One ThreadActor per open DM/channel thread, owning its pty handle, its headless-terminal rendered buffer, and its message history; it receives commands (send-message, stop-turn, open-in-terminal) via a mailbox and emits typed events (message, tool-card, subagent-card, status-change) to WS subscribers and the SQLite writer. Reason: maps 1:1 onto the already-made 'long-lived pty per thread' decision -- the actor's lifecycle IS the pty's lifecycle, so thread-alive/who's-subscribed state never drifts from a separately-tracked state machine, unlike a conventional routes->services->adapters layering.
- (version) Stack versions verified via web search 2026-09-18: node-pty 1.1.0 (stable; 1.2.0-beta.15 exists but staying on stable), @xterm/headless 6.0.0, better-sqlite3 13.0.3, ws 8.21.3, Vite 8.3.0 (create-vite 9.2.1), React 19.3.0. Node.js >=20.19 or >=22.12 required by current Vite.
- (decision) WS wire protocol convention: every backend<->frontend WS frame is a JSON envelope {type, threadId, payload, ts}. Event types emitted by a ThreadActor: 'message.delta' (streaming text chunk), 'message.complete', 'tool-card.open'/'tool-card.update'/'tool-card.close', 'subagent-card.open'/'close' (nested under a parent tool-card id), 'status' (idle|working|needs-input|stopped), 'system' (routing/sync notices). Commands sent to a ThreadActor: 'send-message', 'stop-turn', 'open-in-terminal'. Prevents: each thread type or client screen inventing its own ad hoc message shape.
- (decision) Entity model: Project(id, path, name), Persona(id, agentSkillId, name), Thread(id, projectId, kind: dm|channel, title), ThreadParticipant(threadId, personaId) [1 row for a dm, N for a channel], Message(id, threadId, speakerPersonaId nullable-for-user, kind: text|tool-card|subagent-card|system, content, parentMessageId nullable for subagent nesting, createdAt). Idle-reap: a ThreadActor's pty is killed after a configurable idle window (default 30 min) with no open WS subscriber and no in-flight turn; next message respawns it and Claude Code's own session resume restores conversational context.

- (event) Reviewer gate ran: rubric walker + version-verification lens + adversarial-divergence lens (3 parallel subagents). Version review PASS (minor: don't hardcode create-vite patch, re-resolve at scaffold time). Rubric and adversarial both needs-work; findings triaged and fixed below.
- (decision) Fix (rubric-1): Add-project directory selection cannot use an OS-native file dialog (no Electron) nor the browser File System Access API's showDirectoryPicker (returns a handle, not a filesystem path usable as a pty cwd). New AD-7: the backend exposes a read-only directory-listing endpoint; the frontend renders an in-app breadcrumb directory browser against it, and only the backend-resolved absolute path is ever stored as Project.path.
- (decision) Fix (rubric-2): bootstrap/history data (project list, persona catalog, thread list, paginated message history on open/reconnect) is fetched via a plain REST layer (GET /api/projects, /api/projects/:id/threads, /api/threads/:id/messages) BEFORE opening the thread's WS connection. WS carries only live events/commands for an already-open thread, never initial state.
- (decision) Fix (rubric-3 + adversarial-4): AD-1 clarified -- a ThreadActor owns and self-enforces its own idle timer and crash handling; on unexpected pty exit OR idle-timeout it kills its own pty, emits a 'system' event + status=stopped, persists that status, and THEN tells the registry to deregister it. The registry only creates-if-absent and looks up actors; it never kills a pty or reaches into actor state directly -- deregistration is always actor-initiated, one direction, to prevent a double-kill race or orphaned pty between two independently-built halves.
- (decision) Fix (adversarial-3): AD-2 clarified ownership/order -- a Thread row is created (if absent) before an activation attempt. If activateProject() throws, the owning ThreadActor never spawns the pty; it persists Thread.status=stopped and emits a single 'system' event carrying the failure reason. activateProject.ts is the only owner of activation-failure classification; no other module invents its own retry/fallback path.
- (decision) Fix (adversarial-1): Persona is a GLOBAL catalog table (id, agentSkillId, name), sourced once from BMad's agent config -- never duplicated per project. 'Each persona is a persistent per-project contact' (CAP-3) is realized entirely through Thread rows: a dm-kind Thread is unique on (projectId, personaId), and THAT row -- not a Persona row -- is what's scoped per project.
- (decision) Fix (adversarial-2): unified id convention -- drop the WS-only 'parentToolCardId' field. A tool-card or subagent-card is minted as a Message row (with its id) by the ThreadActor at *.open time, BEFORE the WS event broadcasts; the WS event and the persisted row both carry the same field name parentMessageId referencing that Message.id. One id space, minted in one place.
- (decision) Fix (adversarial-5): a project/persona list view (e.g. a notification tray or sidebar status dots) must NEVER open a live per-thread WS subscription just to read status -- that would silently spawn a pty per project per AD-1's 'spawn on first open/subscribe' wording. Thread gets a persisted status column that a ThreadActor writes on every status change; any list/tray view reads status via the REST bootstrap layer (rubric-2 fix) plus a single lightweight global 'presence' WS channel broadcasting {threadId, status} deltas -- never a per-thread subscription.
